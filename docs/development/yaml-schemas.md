# Edge16 YAML schemas

Edge16 publishes versioned generated JSON Schemas for YAML radio/model files.

Schemas live on the `yaml-schemas` branch and are fetchable without GitHub API authentication.

## Lookup URLs

Latest manifest:

```text
https://raw.githubusercontent.com/onliner10/Edge16/yaml-schemas/v1/latest/manifest.json
```

Version-specific manifest:

```text
https://raw.githubusercontent.com/onliner10/Edge16/yaml-schemas/v1/schema-versions/<schema-version>/manifest.json
```

`v1` is the schema publication layout version. `<schema-version>` comes from `docs/development/yaml-schema-releases.md`.

Each manifest maps supported targets and YAML roots to schema files:

```text
tx16s/model.schema.json
tx16s/radio.schema.json
tx16smk3/model.schema.json
tx16smk3/radio.schema.json
```

Use `tx16s` for TX16S MK2 model/radio YAML and `tx16smk3` for TX16S MK3 YAML.

## YAML schema locator comments

Radio-written model/radio YAML may include a comment preamble:

```yaml
# yaml-language-server: $schema=https://raw.githubusercontent.com/onliner10/Edge16/yaml-schemas/v1/schema-versions/1.0/tx16s/model.schema.json
# edge16-schema-format: 1
# edge16-schema-version: 1.0
# edge16-firmware-commit: <commit>
# edge16-target: tx16s
# edge16-yaml-root: model
```

These are comments only; they are not firmware data fields. The first line is understood by common YAML editor tooling. The `edge16-*` lines give AI/editing tools enough metadata to resolve the exact schema.

Radio settings files with `checksum:` keep that checksum as the first line; schema locator comments follow it so firmware checksum detection stays compatible. `edge16-firmware-commit` is provenance only; schema lookup should use `edge16-schema-version` or the `$schema` URL.

## AI tool lookup flow

1. Read schema locator comments if present and fetch the exact `$schema` URL.
2. Otherwise infer target (`tx16s` or `tx16smk3`), root (`model` or `radio`), and schema version from context.
3. Fetch `v1/schema-versions/<schema-version>/manifest.json`.
4. If schema version is unavailable, fetch `v1/latest/manifest.json` and warn that schema is latest published version, not exact requested version.
5. Fetch the schema URL from the manifest.

## Schema source of truth

The schema generator reads the generated firmware `YamlNode` tables:

- `radio/src/storage/yaml/yaml_datastructs_x10.cpp`
- `radio/src/storage/yaml/yaml_datastructs_tx16smk3.cpp`

Those tables are generated by `radio/util/generate_yaml.py`, so schema publication follows the existing firmware YAML model instead of introducing a second hand-maintained schema.

Custom firmware read/write hooks are represented permissively with `x-edge16-custom-*` metadata. Do not treat those fields as fully semantically constrained until dedicated schema overrides are added.

## Schema release process

`docs/development/yaml-schema-releases.md` is the source of truth for the published schema release version. The top `## <version>` heading becomes the version published under `v1/schema-versions/<version>/`.

CI compares generated schemas with the previously published `v1/latest` schemas. It fails if schemas changed without a release-note version bump. It also fails if breaking changes are detected without a non-empty `### Breaking` section in the new release note entry. The first migration from unversioned manifests may skip old-schema comparison because previous manifests do not have `schemaReleaseVersion` metadata.
